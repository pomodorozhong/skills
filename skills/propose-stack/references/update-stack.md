# Merge and update the stack

Read this when the user asks to merge the stack or part of it, asks to update the remaining PRs, or when a stack this skill opened has a merged PR or a branch that `gh stack view --json` marks with `needsRebase`. The rules in [SKILL.md](../SKILL.md) still apply: the `gh stack` requirements, running it non-interactively, the remote, finding the stack, and the working files.

## Merge

Merge only when the user asks (see step 7 of [SKILL.md](../SKILL.md)). If the user asks to merge, use `gh stack merge <PR number> --yes` with the merge method the user names (`--squash`, `--merge`, or `--rebase`; without one it reuses the last-used method). It merges that PR and every unmerged PR below it, all or nothing; `gh pr merge` cannot merge a stack, and stacked PRs support neither auto-merge nor bypassing merge rules. If the default branch uses a merge queue, the PRs are queued instead and the queue picks the method.

After a merge, check the result: `gh stack view --json` marks each merged branch `isMerged`, and every issue a merged PR's body closes is closed. Report any issue left open and propose closing it; close it only with the user's approval. If PRs remain open, continue with [Keep the stack up to date](#keep-the-stack-up-to-date) from its first step, which also catches what the merge queue has not merged yet; if every PR has merged, go to its **Clean up** step.

## Keep the stack up to date

When PRs at the bottom merge (merging a PR also lands every unmerged PR below it), GitHub rebases the remaining branches itself so the lowest open PR targets the default branch, and the local branches fall behind the remote. GitHub's docs suggest `gh stack sync` here; this skill runs its steps separately so that no force-push happens before the user approves it. A stack also needs a linear history to merge: it loses it when the default branch moves ahead or a lower branch gets new commits, and `gh stack view --json` then marks the branches with `needsRebase`. Rebase locally as below rather than with the **Rebase Stack** button on GitHub: that button force-pushes every branch with no chance to approve the result first, its commits are not signed, and it cannot handle conflicts.

1. **Find what changed:** check out the stack. Before fetching, note each remaining branch's local tip and its remote-tracking tip (`origin/<branch>`). Then fetch, fast-forward the local default branch to `origin/<default>` as in [step 3 of the build](build-and-review.md#3-build-the-stack) (stop and ask if it cannot fast-forward), and run `gh stack view --json` to see which PRs merged and which branches need a rebase. Its PR states are only open, merged, and queued, so check each remaining PR with `gh pr view` too. If a PR was closed without merging, which blocks every PR above it, or a branch is marked `isQueued`, stop and ask. Also compare the local stack with the one on GitHub (`gh api "repos/<owner>/<repo>/stacks?pull_request=<N>"` for any PR in it, whose `pull_requests` run bottom to top): `gh stack sync` would pull down PRs someone added on GitHub, but the steps below do not, so if the two differ, stop and ask. For each merged PR, check that every issue its body closes is now closed; GitHub's stack docs do not say how closing keywords behave for PRs above the bottom. Report any left open and propose closing them; close them only with the user's approval.
2. **Catch up with GitHub:** for each branch whose remote tip changed, such as after GitHub's own rebase, move the local branch to the new remote tip only if its local tip equals the remote-tracking tip noted before fetching, so it holds nothing unpushed: `git branch -f <branch> origin/<branch>`, or `git reset --hard origin/<branch>` for the checked-out branch when its working tree is clean. If it holds unpushed commits, stop and ask. This needs no push.
3. **Rebase only if needed:** if `gh stack view --json` still marks a branch with `needsRebase`, note each remaining branch's current tip, then run `gh stack rebase`, which fetches and rebases the remaining branches onto the default branch, dropping the merged commits. If it exits with code 7, a rebase is already in progress: stop and ask. On a conflict (exit code 3), resolve the files, stage them with `git add`, and run `gh stack rebase --continue`; stop and ask about any conflict that needs a decision, and if the user wants to start over, `gh stack rebase --abort` restores every branch. If it stops because GitHub moved the stack onto a new base after its old base branch was deleted, and the old base's commits did not merge, it asks for `--accept-base-change` before dropping them: stop and ask, and pass that flag only with the user's approval. Run the checks ([step 4](build-and-review.md#4-check-each-layer)) on each rebased branch. Do not use `gh stack sync`, which pushes without asking. If nothing needs a rebase, skip to step 6.
4. **Approval:** for each rebased PR, show the old and new tip, the commits now on the branch, the check results, and the conflicts resolved. Ask: "Force-push these N branches?" and stop.
5. **Publish:** push with `gh stack push`, whose per-branch `--force-with-lease` refuses to overwrite a branch that changed on the remote since the rebase fetched it.
6. **Verify:** check each PR's tip, base, and diff, and that `gh stack view --json` marks no branch with `needsRebase`, and reply with the PRs.
7. **Clean up:** once every PR in the stack has merged, propose `gh stack unstack --local` and deleting the local branches and the working files. Also list each merged PR's branch still on the remote (`git ls-remote --heads origin <branch>` prints it), and propose `git push origin --delete <branch>` for each. Keep the local branches until this step so the user can still look at them; `gh stack` itself does not need them, since its stack record keeps merged branches and their last commits after the local branches are deleted. Do each only with the user's approval.
